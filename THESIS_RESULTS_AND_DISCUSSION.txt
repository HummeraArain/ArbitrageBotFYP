5.1 Evaluation Context
This chapter reports the observed behavior of the implemented system using local
runtime data and the project database. Results are taken from the integrated pipeline
(market scan -> gating -> execution -> persistence -> dashboard feed/ledger).

Current runtime configuration during observations:
- EXCHANGE_TESTNET=true
- COINBASE_PAPER_MODE=true
- AUTO_EXECUTION=true
- REQUIRE_POSITIVE_NET=true
- PROFIT_ONLY_EXECUTION=true
- ENFORCE_AI_SPREAD_GATE=false (AI advisory mode)
- TRADING_FEE_RATE=0.0002
- TRADING_SLIPPAGE_RATE=0.00005

Interpretation note:
- Binance/Bybit routes can run in LIVE mode (as per exchange credentials/state).
- Coinbase routes in this setup run as COINBASE_PAPER (simulated funds with live prices).

--------------------------------------------------------------------------------
5.5 Significance of Results
--------------------------------------------------------------------------------

1) Practical viability:
- The system demonstrates full-stack viability with real-time monitoring, decisioning,
  execution, storage, and UI in one integrated platform.

2) Explainability:
- Decision traceability is significantly improved through execution feed + database logs.
- This directly helps FYP defense because each trade can be explained using stored
  route/status/error/profit context.

3) Safety-first automation:
- The design intentionally blocks non-profitable or unsafe opportunities.
- This prevents overtrading and shows that robustness was prioritized over raw trade count.

4) Research value:
- The architecture can be reused for further academic work in route optimization,
  slippage modeling, and adaptive policy learning.

--------------------------------------------------------------------------------
5.6 Limitations
--------------------------------------------------------------------------------

1) Environment limitation:
- Current measured results are from testnet + Coinbase paper branch configuration.
- Full live-market behavior can differ due to order-book depth, latency, and fees.

2) Cost-model approximation:
- Fee/slippage are configurable but still simplified approximations.
- Exact realized PnL can differ from estimated pre-trade net spread.

3) Route imbalance:
- Most opportunities concentrate on a few routes (e.g., BINANCE -> BYBIT), reducing
  route diversity and potentially overfitting runtime behavior.

4) Asset scope limitation:
- Current implementation is BTC-centric.
- Multi-asset expansion may reveal different spread dynamics and risk patterns.

5) Exchange constraints:
- Insufficient inventory and exchange-side restrictions can still block otherwise valid
  opportunities.

--------------------------------------------------------------------------------
5.7 Threats to Validity
--------------------------------------------------------------------------------

Internal validity threats:
- Runtime configuration changes (.env) affect observed outcomes.
- Network instability may distort real-time API behavior.

External validity threats:
- Results from one machine and selected exchange setup may not generalize equally
  to all infrastructures.

Construct validity threats:
- “Trade success” status indicates execution pipeline success, not guaranteed positive
  economic return for every individual trade.

Mitigation used:
- Rich logging, explicit block reasons, and mode/status-aware evaluation.

--------------------------------------------------------------------------------
5.8 Chapter Summary
--------------------------------------------------------------------------------

The reported results show that ArbPro successfully implements a safe, explainable, and
operational arbitrage workflow. The system achieved strong execution stability
(94.44% success rate in observed records), extensive persistence/auditing, and practical
operator visibility through dashboard charts, feed, and ledger.

At the same time, findings confirm that profitability depends heavily on realistic
cost modeling, route inventory, and runtime conditions. These observations motivate
future improvements in slippage estimation, route balancing, and live-environment
calibration.
