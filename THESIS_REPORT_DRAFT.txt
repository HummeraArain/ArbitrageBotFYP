SUMMARY / ABSTRACT
--------------------------------------------------------------------------------
This project presents an AI-assisted cryptocurrency arbitrage system that monitors
price differences across Binance, Bybit, and Coinbase and executes route-based
arbitrage decisions under strict safety gates. The system combines FastAPI backend
services, CCXT exchange connectivity, WebSocket-based real-time broadcasting, a
React dashboard, a SQLite trade ledger, and machine-learning components.

The core engine continuously computes pair spreads among live exchanges, estimates
net spread after configurable costs, and applies multiple execution gates including:
spread threshold, net profitability, AI decision confidence, inventory precheck, and
risk breaker status. Only opportunities that pass the complete gate sequence proceed
to execution. Every successful or failed execution is logged in the database with route,
mode, status, profit, and error metadata.

A chat assistant is integrated for crypto-domain question answering and can also read
local trade history from the project database. The dashboard includes vault status,
oracle prices, spread monitoring, execution ledger, and a dedicated execution feed for
real-time reasoning messages. The system currently supports testnet/live exchange
switching via environment configuration and Coinbase simulated-funds mode with live
market prices.

As of the extracted local database snapshot (11 April 2026), the project has recorded
659 trades (622 success, 37 failed), with a cumulative successful-trades profit of
approximately 6785.71 USD in stored records. This confirms end-to-end integration
from market scan to persisted execution history.

CHAPTER 1: INTRODUCTION
================================================================================

1.1 Background
Cryptocurrency markets are fragmented across exchanges, creating temporary price
differences for the same asset pair. Arbitrage systems attempt to exploit these
differences by buying on one exchange and selling on another. However, naive
arbitrage logic often fails due to fees, slippage, route inventory constraints, and
execution latency.

1.2 Problem Statement
Manual arbitrage is too slow for fast-moving crypto spreads, while automated systems
without robust guards can execute losing trades. A practical FYP challenge is to build
an end-to-end bot that:
- detects opportunities in real time,
- avoids unsafe trades,
- logs outcomes reliably,
- and exposes clear operator visibility in UI.

1.3 Project Objectives
Primary objectives achieved in this project:
- Build real-time multi-exchange price monitor (Binance, Bybit, Coinbase).
- Implement route-based arbitrage engine with threshold and net-profit gates.
- Add AI-assisted decision and risk-aware position sizing.
- Store trade history and decision artifacts in SQLite.
- Provide dashboard with live prices, spreads, vault status, ledger, and execution feed.
- Integrate chat assistant for crypto Q/A and local trade-history responses.

CHAPTER 2: LITERATURE REVIEW
================================================================================

2.1 Exchange Arbitrage Systems
Existing crypto arbitrage systems generally use one of three approaches:
- simple threshold-based bots,
- statistical spread predictors,
- AI-assisted decision engines.

Threshold-only systems are easy to deploy but frequently overtrade during noisy
micro-spread conditions. Profit can disappear when costs are ignored.

2.2 Cost-Aware Arbitrage
A known best practice is profitability gating using:
net_spread = gross_spread - (fees + slippage)
This project explicitly applies this guard before execution, which prevented many
loss-making trades in low-spread windows.

2.3 Risk-Gated Execution
Research and production systems often include kill-switches and risk limits. This
project includes:
- daily drawdown breaker,
- optional consecutive-loss breaker,
- Kelly-inspired size control tied to historical outcomes and AI confidence.

2.4 Explainability and Operator Trust
A major practical issue in trading bots is black-box behavior. The implemented execution
feed and database logging address this by reporting route, reason, and outcome events.

2.5 Gap Addressed by This FYP
The project bridges a practical gap: combining multi-exchange scan, AI decisioning,
risk gating, trade persistence, and operator-facing UX in one integrated academic
system suitable for demo and defense.

================================================================================

3.1 Overall Research Design
Methodology used: Design-and-Implement with iterative verification.
Major phases:
1) Environment and exchange integration,
2) Core arbitrage logic,
3) Safety/risk controls,
4) Data persistence,
5) UI and operator interaction,

3.2 System Architecture
A) Backend (FastAPI, asyncio, CCXT):
- continuous arbitrage loop,
- REST endpoints for auth/history/threshold/chat/snapshot,
- WebSocket endpoint for live market and event streaming.

B) AI Layer:
- AIAgent for execution-side opportunity analysis (Gemini with Groq fallback).
- ChatBot for OpenAI-powered crypto-domain assistant responses and DB-aware trade
  history answers.
- GRU predictor for spread trend assistance and periodic auto-retraining from DB.

C) Data Layer:
- SQLite with WAL mode.
- Tables: trades, llm_decisions, market_analysis.

D) Frontend (React + TypeScript):
- Home, Login, Dashboard, Blog.
- Dashboard pages: overview, activity, database.
- Sidebar tabs: chat and execution feed.

3.3 Core Decision Pipeline
The engine evaluates opportunities in this sequence:
1) Fetch live prices and balances.
2) Build all pair routes among currently tradeable exchanges.
3) Select best spread route (with diversification logic).
4) Compute total costs and net spread.
5) Check threshold gate, net gate, AI gate, risk gate.
6) Run precheck for route inventory and balances.
7) Execute trade (or block with reason), then broadcast and persist.

3.4 Profitability Formula
Gross spread (%) computed from route buy/sell prices.
Net spread (%) = gross spread - (TRADING_FEE_RATE + TRADING_SLIPPAGE_RATE)*100
Execution can be blocked even when gross spread > threshold if net spread <= minimum.

3.5 Risk Method
- Daily drawdown breaker.
- Consecutive-loss breaker (configurable).
- Kelly-style position sizing from recent trade statistics and AI confidence.

3.6 Model Training Method
The GRU model uses spread sequences from llm_decisions table.
Auto-train trigger:
- after configured number of trades,
- and minimum interval elapsed.
Model/scaler are reloaded into runtime when retraining succeeds.

3.7 Validation Approach
Validation includes:
- API endpoint behavior,
- WebSocket event continuity,
- trade ledger updates,
- UI rendering of market, spread, feed, and status,
- database-level result checks.

- Chat and execution reasoning separated for clarity.

5.4 Discussion of Trade Blocking Cases
A frequent operator confusion case was:
- gross spread above threshold but no trade execution.
Root cause:
- net spread after costs became non-positive, so safety gate blocked execution.
This is expected behavior for loss prevention.

5.5 Limitations
- Live execution quality depends on exchange API stability and latency.
- Fee/slippage approximation may differ from exact fill realities.
- Route opportunities can cluster, causing one route dominance.
- Current scope is mainly BTC cross-exchange arbitrage workflow.

5.6 Reliability and Security Notes
- JWT-based protected endpoints were implemented.
- Password hashing uses passlib with pbkdf2_sha256 in current code.
- Trade persistence and audit logs improve post-trade accountability.

APPENDIX C: SHORT VIVA PREP Q/A
================================================================================

Q1: Why does bot block trades even when spread is above threshold?
A: Because threshold checks gross spread. Final execution uses net spread after fees
   and slippage; if net is non-positive, trade is blocked.

Q2: How do you prove the bot actually executed trades?
A: trades table in SQLite stores timestamp, route, mode, status, profit, and errors.
   Dashboard execution ledger reads this table via /api/history.

Q3: How is safety enforced?
A: Multi-gate pipeline: spread gate, net-profit gate, AI gate, risk breaker, and
   pre-execution inventory checks.

Q4: Is your system only UI demo or full-stack?
A: Full-stack. Backend trading loop, exchange APIs, DB persistence, and real-time UI
   are fully integrated.
